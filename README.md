# LLM Inference Simulators

How to build, accelerate, validate and integrate simulators for LLM inference and novel AI hardware. Eleven interactive decks run from *why* architecture teams simulate (and how software-level models relate to RTL simulation), through a hands-on simulator-development tutorial in SimPy, the physics of LLM serving and the existing simulator landscape, to a **live disaggregated-serving simulator in the browser**, then metrics and validation, **power and energy** (DVFS, power caps, joules per token), acceleration techniques, and integration with PyTorch, ONNX Runtime and HEIR. A reading list and a role primer close the series.

**Live index:** https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/

## How to read this series

Decks 01–02 are about simulators in general and stand alone. Decks 03–05 apply them to LLM serving and culminate in the live simulator. Decks 06–09 cover what turns a simulator into an engineering tool: trustworthy metrics, power and energy, simulator speed, and integration with real frameworks. Deck 10 is a reading list (books, courses, papers, tutorials, source code); deck 11 applies the whole series to a real, publicly advertised simulation-and-frameworks role.

## Glossary: concepts and where they are explained

Every concept the decks rely on, with links to the slides that explain it in depth (this series, the Local LLM Hosting and Key Publications decks, or the FHE Accelerator Simulators glossary). The same glossary, with anchors each deck links to, is on the [live index](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#glossary).

| Concept | What it is | Where it is explained |
|---|---|---|
| The fidelity ladder | The range of model detail from analytical formulas through discrete-event, transaction-level, cycle-level and RTL simulation to emulation, FPGA prototypes and silicon. Each rung is slower and more detailed; use the highest rung that answers the question. | [InfSim 01 · the fidelity ladder](https://brendanjameslynskey.github.io/InfSim_01_Why_Simulate/#slide-03); [InfSim 01 · what each level throws away](https://brendanjameslynskey.github.io/InfSim_01_Why_Simulate/#slide-04); [InfSim 01 · how long it would take](https://brendanjameslynskey.github.io/InfSim_01_Why_Simulate/#slide-05) |
| Discrete-event simulation (DES) | A simulator whose state changes only at instants (events). A clock, a state, a time-ordered event list and handlers; the clock jumps from one event to the next (next-event time advance), so idle time costs nothing. | [InfSim 02 · anatomy of a DES](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-01); [InfSim 02 · a kernel in 30 lines](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-02); [InfSim 02 · step through the event list](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-04) |
| Process interaction and coroutines | Writing each entity's life as one sequential function that suspends while it waits, instead of scattering it over event handlers. Python generators make this natural: yield an event, resume when it fires. | [InfSim 02 · generators as coroutines](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-05) |
| SimPy | A small, pure-Python DES library: Environment, processes, timeouts, events, Resource, Container, Store and interrupts. It has no built-in statistics or tracing; the probes are yours to design. | [InfSim 02 · the whole vocabulary](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-06); [InfSim 02 · modelling hardware in SimPy](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-07) |
| Resources, stores, containers and back-pressure | Resource: N identical servers held for a while (links, engines). Store: a buffer of items (FIFOs). Container: an amount (credits, bytes). A finite-capacity Store makes producers wait when it is full, which is back-pressure. | [InfSim 02 · modelling hardware in SimPy](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-07) |
| FCFS hold versus processor sharing | Two ways to model a shared link: one transfer holds it at full rate while others queue, or all active transfers share it equally. Throughput and utilisation match; latency distributions do not. | [InfSim 02 · hold the link or share it?](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-08) |
| Cost model | The part of a simulator that answers "how long does this take?" (and, with a power model, "how many joules?"). Kept separate from the event engine so a roofline can later be replaced by a measured table or an RTL-calibrated model. | [InfSim 02 · structuring a simulator](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-09); [InfSim 03 · a cost-model checklist](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-10); [InfSim 04 · inside Vidur](https://brendanjameslynskey.github.io/InfSim_04_Simulator_Landscape/#slide-03) |
| Determinism, tie-breaking and RNG streams | Same configuration and seed must give bit-identical results: break ties between simultaneous events with a sequence number, prefer integer time for clocked models, and give each component its own random stream. | [InfSim 02 · time, ordering and determinism pitfalls](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-10); [InfSim 02 · the tie-breaking sequence number](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-02) |
| Transaction-level modelling (SystemC TLM-2.0) | Modelling bus reads and writes as function calls with annotated delays rather than signal wiggles. Loosely-timed TLM boots software; approximately-timed TLM models contention. The industry route to virtual platforms. | [InfSim 02 · beyond Python](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-12); [InfSim 04 · system and network simulators](https://brendanjameslynskey.github.io/InfSim_04_Simulator_Landscape/#slide-05) |
| RTL simulation, co-simulation and golden models | The software model is the executable specification and the golden reference (a scoreboard in the RTL testbench). RTL cycle counts calibrate the model, workload traces become directed tests, and co-simulation embeds RTL blocks in the system model. | [InfSim 01 · software-level simulators and RTL](https://brendanjameslynskey.github.io/InfSim_01_Why_Simulate/#slide-06); [InfSim 01 · the co-flow](https://brendanjameslynskey.github.io/InfSim_01_Why_Simulate/#slide-07); [InfSim 01 · co-simulation in practice](https://brendanjameslynskey.github.io/InfSim_01_Why_Simulate/#slide-08) |
| Serving, accelerator and network simulators | Serving simulators (Vidur, LLMServingSim, SplitwiseSim) model request streams and schedulers; accelerator models (LLMCompass, Timeloop, SCALE-Sim) model compute arrays; system simulators (ASTRA-sim, gem5, SST) model networks and memory. | [InfSim 04 · which question, which level?](https://brendanjameslynskey.github.io/InfSim_04_Simulator_Landscape/#slide-01); [InfSim 04 · side by side](https://brendanjameslynskey.github.io/InfSim_04_Simulator_Landscape/#slide-06); [InfSim 04 · inside Vidur](https://brendanjameslynskey.github.io/InfSim_04_Simulator_Landscape/#slide-03) |
| Prefill and decode | Prefill processes the whole prompt in one pass (matrix-matrix, compute-bound) and produces the first token. Decode then generates one token per sequence per step (matrix-vector, memory-bound). They need different hardware balances. | [InfSim 03 · two phases](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-01); [InfSim 05 · the interference problem](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-01) |
| FLOP and byte counting | About 2 FLOPs per matmul parameter per token, plus attention that grows with context. A decode step must also read every weight and all of the KV cache. These two counts drive every timing and energy number in the series. | [InfSim 03 · counting FLOPs](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-02); [InfSim 03 · counting bytes](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-03) |
| Roofline, arithmetic intensity and ridge point | Attainable performance is the lower of peak compute and bandwidth × arithmetic intensity (FLOPs per byte). The ridge point is the intensity at which both limits meet; below it a kernel is memory-bound. | [InfSim 03 · the roofline](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-04); [InfSim 03 · interactive roofline](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-05); [Key Publications 04 · FlashAttention as IO-awareness](https://brendanjameslynskey.github.io/Papers_04_Efficient_Inference/#slide-01); [SimEng 12 · the roofline as an analytic bound](https://brendanjameslynskey.github.io/SimEng_12_Measurement_Tools_and_Methods/#card-bounds) |
| KV cache | The stored keys and values of every token of every live sequence, so attention need not recompute them. Its size (320 KiB per token for Llama-3-70B) limits batch size and is what disaggregation must move. | [InfSim 03 · KV-cache arithmetic](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-06); [Local LLM 03 · why the KV cache dominates serving](https://brendanjameslynskey.github.io/Local_LLM_03_vLLM_Architecture/#slide-01) |
| Continuous batching | Re-forming the batch at every decode iteration: finished sequences leave and new ones join, so the GPU stays full. The scheduler loop at the heart of every serving engine and serving simulator. | [InfSim 03 · batching](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-07); [Local LLM 03 · iteration-level scheduling](https://brendanjameslynskey.github.io/Local_LLM_03_vLLM_Architecture/#slide-05) |
| PagedAttention | Storing the KV cache in fixed-size blocks with a per-sequence block table, like virtual memory, which removes fragmentation and allows prefix sharing. | [Local LLM 03 · PagedAttention](https://brendanjameslynskey.github.io/Local_LLM_03_vLLM_Architecture/#slide-03); [Key Publications 04 · the vLLM paper](https://brendanjameslynskey.github.io/Papers_04_Efficient_Inference/#slide-04); [InfSim 03 · batching](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-07) |
| Chunked prefill | Splitting long prompts into chunks and mixing them with decode tokens in each step, which bounds how long decodes stall. The alternative to disaggregation for the same interference problem. | [InfSim 03 · batching](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-07); [Local LLM 03 · prefix caching and chunked prefill](https://brendanjameslynskey.github.io/Local_LLM_03_vLLM_Architecture/#slide-06) |
| Tensor, pipeline and expert parallelism | Splitting a model across devices by weight matrix (TP: all-reduces per layer), by layer (PP: activations between stages) or by expert (EP: all-to-all). Each adds communication a simulator must cost. | [InfSim 03 · parallelism and its bill](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-08); [Local LLM 05 · tensor parallel](https://brendanjameslynskey.github.io/Local_LLM_05_Multi_GPU_Parallelism/#slide-02); [Local LLM 05 · expert parallel](https://brendanjameslynskey.github.io/Local_LLM_05_Multi_GPU_Parallelism/#slide-05) |
| Quantisation | Storing weights (and sometimes activations or KV) in fewer bits. It shrinks the dominant byte term of decode, so it helps bandwidth-bound decode far more than compute-bound prefill. | [InfSim 03 · counting bytes](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-03); [Local LLM 07 · why quantise](https://brendanjameslynskey.github.io/Local_LLM_07_Quantization/#slide-01); [Local LLM 07 · FP8 and beyond](https://brendanjameslynskey.github.io/Local_LLM_07_Quantization/#slide-06) |
| TTFT, TPOT and inter-token latency | Time to first token (prefill queueing and compute); time per output token after the first (DistServe's definition); and the gap between consecutive tokens, whose tail shows stalls the mean hides. | [InfSim 03 · the metrics users feel](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-09); [InfSim 05 · the interference problem](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-01) |
| Goodput and SLO attainment | The rate of requests that meet every SLO (for example TTFT ≤ 1 s and TPOT ≤ 25 ms), rather than raw throughput. The metric DistServe optimises and the simulator reports. | [InfSim 03 · the metrics users feel](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-09); [InfSim 05 · the idea: split the phases](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-02); [InfSim 05 · results](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-08) |
| Percentiles and tail-latency CCDFs | Report p50, p90 and p99, not means, and plot the fraction of samples slower than x on log-log axes, where tails show. Say which population (all tokens or per request), and use streaming sketches when samples are many. | [InfSim 06 · distributions, not averages](https://brendanjameslynskey.github.io/InfSim_06_Metrics_Hotspots_Validation/#slide-02); [InfSim 05 · the live CCDF](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-06) |
| Utilisation, MFU and MBU | Busy fraction says how often a resource works; model FLOPs and bandwidth utilisation say how much of its capability it uses. A continuous-batching decode engine is 100% busy at 4% MFU and about 77% MBU. | [InfSim 06 · utilisation and efficiency](https://brendanjameslynskey.github.io/InfSim_06_Metrics_Hotspots_Validation/#slide-03); [InfSim 05 · the simulator's resource table](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-06) |
| Little's law and the operational laws | L = λW: mean population equals arrival rate times mean time in system, for any stable system. With the utilisation and forced-flow laws it gives free consistency checks on a simulator's probes. | [InfSim 06 · operational laws](https://brendanjameslynskey.github.io/InfSim_06_Metrics_Hotspots_Validation/#slide-03); [InfSim 02 · exercise: test Little's law](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-13) |
| Hot-spot attribution | Finding where speeding things up would help most. A stage breakdown that sums exactly to each request's latency, the largest waiting stage mapped to the resource that owns it, confirmed by what-if sensitivity runs. | [InfSim 06 · hot-spot attribution](https://brendanjameslynskey.github.io/InfSim_06_Metrics_Hotspots_Validation/#slide-04); [InfSim 05 · experiment: starve the link](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-07) |
| Chrome trace events and Perfetto | A JSON timeline format (complete slices, counters, metadata) that Perfetto and chrome://tracing display. The simulator, ONNX Runtime's profiler and RTL testbenches can all emit it, so timelines can be compared side by side. | [InfSim 06 · traces in Perfetto](https://brendanjameslynskey.github.io/InfSim_06_Metrics_Hotspots_Validation/#slide-05); [InfSim 09 · ONNX Runtime's profiler](https://brendanjameslynskey.github.io/InfSim_09_Framework_Integration/#slide-07); [SimEng 12 · Perfetto, as a measurement tool](https://brendanjameslynskey.github.io/SimEng_12_Measurement_Tools_and_Methods/#card-perfetto) |
| Prefill–decode interference | On a colocated server a waiting prefill runs before the next decode step, so every sequence mid-generation stalls for the whole prefill: mean TPOT moves a little, p99 inter-token latency jumps about tenfold. | [InfSim 05 · the interference problem](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-01); [InfSim 03 · two phases](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-01) |
| Disaggregated (prefill/decode) serving | Running prefill and decode on separate machine pools (Splitwise, DistServe, Mooncake, NVIDIA Dynamo), so each phase is provisioned and power-managed for its own SLO. The cost is moving the KV cache. | [InfSim 05 · split the phases](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-02); [InfSim 05 · in production](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-03); [InfSim 05 · live simulator](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-06) |
| KV-cache transfer | Bytes = prompt tokens × KV per token (671 MB for a 2k-token Llama-3-70B prompt): 1.5 ms on NVLink, 13 ms on InfiniBand NDR, 215 ms on 25 GbE. The link and its queue can become the hot-spot. | [InfSim 05 · what the KV transfer costs](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-04); [InfSim 05 · experiment: starve the link](https://brendanjameslynskey.github.io/InfSim_05_Disaggregated_Inference/#slide-07) |
| Encoder-only prefill (causal encoder-decoder) | A model whose prefill runs only part of the network: in DeepSeek-V4.1-Flash's Causal Encoder-Decoder the bottom half of the layers is a causal encoder and every decoder layer projects its KV from the last encoder state, so a prompt token activates 8B parameters and a generated token 16B. ## Where this fits

Part of the [LLMs hub](https://github.com/BrendanJamesLynskey/LLMs), under *Hardware & Inference*. Complements [Local LLM Hosting](https://github.com/BrendanJamesLynskey/LLM_Hub_Local_LLM_Hosting) (the real serving engines these simulators model), [NVIDIA GPU Architectures](https://github.com/BrendanJamesLynskey/LLM_Hub_NVIDIA_GPUs) and [Google TPUs](https://github.com/BrendanJamesLynskey/LLM_Hub_Google_TPUs) (the hardware in the cost models), and the [Key LLM Publications](https://github.com/BrendanJamesLynskey/LLM_Hub_Key_Publications) efficient-inference deck.

**Sister series:** [FHE Accelerator Simulators](https://github.com/BrendanJamesLynskey/FHE_Hub_Accelerator_Simulators) ([live](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/)) applies the same methods (SimPy, metrics and hot-spots, power under a TDP, a bit-exact JavaScript port) to an FHE accelerator running CKKS bootstrapping, with code in [FHE_Accelerator_Sim](https://github.com/BrendanJamesLynskey/FHE_Accelerator_Sim).

**Sister series:** [Fourier Optics for Inference](https://github.com/BrendanJamesLynskey/LLM_Hub_Fourier_Optics_Inference) ([live](https://brendanjameslynskey.github.io/LLM_Hub_Fourier_Optics_Inference/)) extends this series' simulator with heterogeneous pools, FFT-mixing models and an optical transform engine in the prefill pool, with a break-even analysis and the KV hand-off options.

**Related series:** [Simulation Engineering Toolkit](https://github.com/BrendanJamesLynskey/SimEng_Hub_Toolkit) ([live](https://brendanjameslynskey.github.io/SimEng_Hub_Toolkit/)) covers the engineering around a simulator: a bit-exact Rust port of this series' simulator with PyO3 ([Rust_DES_Kernel](https://github.com/BrendanJamesLynskey/Rust_DES_Kernel)), testing frameworks, CI, specifications and more.

**Related site:** [LLM Inference Explained](https://llm-inference-explained.vercel.app/) ([code](https://github.com/BrendanJamesLynskey/llm-inference-explained)) is an interactive web explainer of real decoder inference: the KV cache, the roofline, batching, paged memory, speculative decoding and serving metrics, then disaggregated serving with this series' simulator engine (`web/sim_engine.js`, pinned to a commit) running live in the browser.
